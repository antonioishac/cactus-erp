- **PRIMEIRA SUBIDA REAL (2026-08-23)**: `cadastro-base-service` rodou fim a fim pela primeira vez contra o `cactus-mysql` do usuário (schemas provisionados via `provisionamento-mysql-local.sql`) — Flyway aplicou as 7 migrations, Hibernate validou o schema, Tomcat subiu na porta 8081, Swagger UI/OpenAPI/JWKS respondendo, seed completo confirmado (5 papéis, 22 funcionalidades, 1 usuário admin, 1 empresa, 3 NCM, 1 grupo tributário, 2 configurações tributárias SP+MG, 2 linhas de ICMS, 3 clients OAuth2). Dois bugs reais só apareceram nesta subida (nenhum dos dois existia em `mvn compile`, só em runtime):
  1. **Flyway não rodava silenciosamente** — Boot 4.1 modularizou o autoconfigure do Flyway num artefato próprio (`org.springframework.boot:spring-boot-flyway`), igual já tinha acontecido com o OAuth2 Authorization Server; ter só `flyway-core`/`flyway-mysql` no classpath não bastava. Corrigido adicionando a dependência no `pom.xml` do `cadastro-base-service`.
  2. **`SituacaoConverter` não era descoberto pelo Hibernate** — `CactusCadastroBaseApplication` tinha só `@SpringBootApplication(scanBasePackages = "br.com.cactusdigital.erp")`, e eu tinha documentado (errado) que isso também estenderia o escaneamento de `@Entity`/`@Converter`. Na real, `scanBasePackages` só afeta `@ComponentScan`; o escaneamento JPA (incluindo `@Converter(autoApply=true)`) é um mecanismo separado que, sem `@EntityScan` explícito, usa só o pacote da classe principal (`...erp.cadastro`) — `SituacaoConverter`, em `common.domain`, nunca era encontrado, e o Hibernate caía no mapeamento padrão de enum (`ORDINAL`→`TINYINT`), batendo com a coluna `CHAR(1)` das migrations. Corrigido com `@EntityScan(basePackages = "br.com.cactusdigital.erp")` explícito (pacote novo no Boot 4.1: `org.springframework.boot.persistence.autoconfigure.EntityScan`, não `...autoconfigure.domain`).
  Também corrigidos nesta passada: `spring.application.name` e client_ids OAuth2 de serviço ainda tinham o prefixo `cactus-` redundante (`cactus-cadastro-base-service`→`cadastro-base-service`, `cactus-estoque-service`/`cactus-compras-service`→`controle-estoque-service`/`gestao-compras-service`, batendo com os nomes de módulo reais do roadmap) — achado ao revisar o `provisionamento-mysql-local.sql` a pedido do usuário.

- **EXTRAÇÃO DO `seguranca-service` (2026-08-29)**, a pedido do usuário, antes de começar a Fase 2 — motivo: validar um JWT não exige chamada síncrona ao emissor (o Resource Server cacheia a chave pública via JWKS), então o acoplamento de separar Authorization Server + RBAC do resto é fraco; e o catálogo de `Funcionalidade` já era intrinsecamente cross-cutting (protege endpoint de qualquer módulo, não só cadastro base) — não devia morar dentro de um serviço de negócio específico. Sistema ainda não homologado, então foi refatoração livre (schema de banco, nomes de authority, estrutura), não migration incremental por cima do que já tinha rodado.
  - **O que saiu do `cadastro-base-service` e virou `seguranca-service`** (porta 8082, schema `cactus_seguranca`, package `br.com.cactusdigital.erp.seguranca`): `Usuario`/`Papel`/`Funcionalidade`/`Modulo`/`UsuarioPapelEmpresa` (entity/repository/service/controller/dto/mapper), `AuthorizationServerConfig`/`JdbcAuthorizationServerConfig`/`JwtKeyConfig`/`OAuth2ClientSeeder`/`PasswordEncoderConfig`/`ResourceServerConfig` (config de segurança), `UsuarioDetailsService`/`TokenClaimsService`, `AuthController`/`DevAuthController`. O `cadastro-base-service` vira Resource Server puro: perdeu a dependência `spring-boot-starter-oauth2-authorization-server`, o `.formLogin(...)` do `ResourceServerConfig`, e passou a apontar `spring.security.oauth2.resourceserver.jwt.jwk-set-uri` pro `seguranca-service` (`jwk-set-uri`, não `issuer-uri`, de propósito — não acopla ordem de subida dos dois serviços; `issuer-uri` faz *discovery* e podia falhar o boot se o seguranca-service não estivesse de pé ainda).
  - **Referências cross-serviço viram `Long` solto, sem FK, sem validação de existência na v1** (decisão registrada, não escondida): `Usuario.colaboradorId` e `UsuarioPapelEmpresa.empresaId` — `Colaborador`/`Empresa` moram no cadastro-base-service, em outro schema. Consequência direta: `empresaNome` saiu de todo lugar que mora no seguranca-service (`MeResponse`, `EmpresaDisponivelResponse`, `UsuarioPapelEmpresaResponse`, `TrocarEmpresaResponse`, `DevLoginResponse`, claim do JWT) — só `empresaId` — porque resolver o nome exigiria chamar o cadastro-base a cada emissão de token, tornando o login uma dependência síncrona forte do cadastro-base estar de pé. Quem precisa do nome resolve a partir do `empresaId` no serviço que já tem esse dado. Fica pro roadmap: se um dia for necessário validar de verdade os ids na escrita (criar usuário/atribuir papel-empresa), entra um client HTTP com token de serviço auto-emitido chamando a API já existente do cadastro-base — não construído agora, deliberadamente.
  - **Authorities renomeadas**: `CADASTRO_SEGURANCA_CONSULTAR`/`CADASTRO_SEGURANCA_GERENCIAR` (faziam parte do módulo `CADASTRO_BASE`, o que não fazia mais sentido fora dele) → `SEGURANCA_CONSULTAR`/`SEGURANCA_GERENCIAR`, novo `Modulo` `SEGURANCA`. As demais (`CADASTRO_CLIENTE_*`, `CADASTRO_PRODUTO_*`, `CADASTRO_EMPRESA_*`, `CADASTRO_COLABORADOR_*`, `CADASTRO_TRIBUTACAO_*`) não mudaram de nome — só de dono: o catálogo (tabela `funcionalidade`) inteiro agora mora no `seguranca-service`, mesmo protegendo endpoint do cadastro-base, exatamente porque RBAC é cross-cutting. Todo módulo futuro semeia as próprias funcionalidades lá, não no próprio banco.
  - **`REGIME_TRIBUTARIO_ANO_DUPLICADO`/`CONFIGURACAO_TRIBUTARIA_DUPLICADA`/`USUARIO_PAPEL_EMPRESA_DUPLICADO`** (achado numa revisão de sessão anterior) já tinham sido corrigidos de `BusinessException`/422 pra `ConflictException`/409 antes desta extração — `USUARIO_PAPEL_EMPRESA_DUPLICADO` foi junto pro novo `SegurancaErrorCode` do `seguranca-service`; `CadastroErrorCode` (cadastro-base) ficou só com os códigos de negócio que não são RBAC.
  - **Ganho pedido explicitamente pelo usuário**: `UsuarioController` ganhou `PATCH /usuarios/{id}/inativar`/`/reativar` (desativação deliberada, reversível, distinta de `bloquear`/`desbloquear` — travamento temporário — e de `excluir` — definitivo). `UsuarioRequest.ativo` deixou de ser reescrito por `PUT /usuarios/{id}` (mesmo padrão que `bloqueado` já seguia: só muda por endpoint de ação dedicado, nunca por PUT genérico).

- **Sessão multi-empresa e `refresh_token` (2026-08-30)** — limitação real encontrada validando o fluxo de auth, registrada, não escondida: o fluxo OAuth2 padrão (`/oauth2/token`, Authorization Code + PKCE) já devolve `access_token`+`refresh_token`+`expires_in` completos, sem nada faltando — isso é o Spring Authorization Server oficial. O problema é a combinação com `POST /api/v1/auth/trocar-empresa`: esse endpoint minta um JWT à parte (mesma chave, sem `OAuth2Authorization` persistido — por isso não tem `refresh_token` próprio, de propósito, ver Javadoc de `AuthController`), então quando o token *original* é renovado pelo `refresh_token` padrão, o `jwtTokenCustomizer` (`AuthorizationServerConfig`) sempre resolve a empresa padrão de novo — não tem como saber que o usuário tinha trocado de empresa antes. **Decisão (opção escolhida pelo usuário)**: não mexer em código agora — resolver client-side. O frontend precisa: (1) guardar qual empresa está ativa; (2) manter o `access_token`/`refresh_token` originais do login pra continuidade de sessão (renovando normalmente); (3) sempre que o usuário estiver operando fora da empresa padrão, chamar `trocar-empresa` de novo depois de cada refresh, antes de bater na API de negócio. Alternativa mais robusta pra quando isso virar problema de verdade (não implementada agora): persistir a empresa ativa como atributo do `OAuth2Authorization` (coluna `attributes`, já existe no schema) e o customizer ler de lá no refresh, em vez de sempre cair no padrão.
